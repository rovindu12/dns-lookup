Proxies aren't available on this site. Checking a proxy means connecting to whatever address you give it and relaying traffic through it — safe to do from your own machine, but not from a public server that anyone could point at anything. Run this tool locally to use it: open a terminal in the project folder and run ./start.sh (or node server.js), then open http://127.0.0.1:8765. That gets you the Proxies box (exit IP, location, ISP, WHOIS, and the DNS servers each proxy uses) plus private/LAN DNS servers and any port.

One per line: host:port, user:pass@host:port, host:port:user:pass, or with a http://, https:// or socks5:// prefix. The lookups then run from each proxy's network. With DNS servers listed, queries travel over TCP inside the tunnel: SOCKS5 proxies usually allow that, HTTP proxies often only allow port 443 and will show as refused. Without DNS servers, the selected resolver is queried through each proxy; choose Google to compare locations, because it passes the proxy's network on to each domain's DNS servers.

Each proxy is asked to look up 16 unique test names, and the public test service bash.ws reports which DNS servers asked, so this contacts bash.ws. This finds DNS servers that actually answered during the check; a residential ISP's full resolver pool is often larger, and a longer real browsing session can surface more of it. Once a proxy's exit IP is known, its location, ISP and network registry are also looked up (from ip-api.com and the RDAP WHOIS system) — free-tier geolocation, so city-level placement is a rough estimate from the network's registered address, not a physical trace. The sites box is optional: leave it empty to check only the proxies (their addresses, exit IPs, location and DNS servers).

Each proxy row also gets a changes IP / no change pill (compares the proxy's exit IP against this computer's own direct connection, shown below the table) and, when set, whether the proxy itself is going through Cloudflare WARP — the same two signals "Your connection" shows for your browser, run here from the server's side for each proxy instead.

This cannot show a proxy's WebRTC leak, browser or TCP/TLS fingerprint (OS, JA3/JA4, HTTP headers) or browser language. Those all come from a real browser's own network stack opening a connection at the OS level — WebRTC in particular does not travel through an HTTP/SOCKS proxy at all, so there is nothing a proxy-mediated request could show for it. This checker asks the proxy itself to make each connection instead, which is a different mechanism; showing browser-only data here would describe this computer, not the proxy, so none is shown. To see that data for a proxy, the browser or operating system itself would need to be configured to use it as its own network connection, then visit a fingerprinting site directly.

Record types

Lookups run in your browser through DNS-over-HTTPS, so the domains you enter are sent to the resolver you pick. IP details are two more DNS lookups per address to that resolver: reverse DNS, and the network owner from Team Cymru's IP-to-ASN mapping (the prefix's registry country, not a physical location). DNS servers you list are queried by your local server directly, and proxies carry those queries or the resolver's from their own network, so answers reflect that location. Proxy credentials stay on your machine and are never shown or exported. To find a proxy's DNS servers, your local server makes each proxy look up random test names and asks the public test service bash.ws which DNS servers asked; bash.ws never sees your sites. A proxy's exit IP is also looked up at ip-api.com (location, ISP, usage type) and in the RDAP WHOIS system (registry, network name and range) — both public lookups of an address already known from the proxy, not sent through it. The domains and DNS server addresses you enter are also sent to this site's server function, which runs those lookups; it only sends DNS queries and never connects to private or local addresses. The connection panel asks this site's server which address your request came from (or Cloudflare when this page is not on the hosted site), asks Cloudflare (icanhazip.com) for your IPv4 and IPv6 addresses, and asks Cloudflare's STUN server to test whether WebRTC exposes another address. Answers come from caching resolvers, so a TTL is the time left in the cache (at most the zone's TTL), and load-balanced names can return different addresses from one query to the next.
